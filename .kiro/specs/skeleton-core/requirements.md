# Skeleton Core - Requirements

## Overview

The skeleton core (`@skeleton/core`) is a reusable, app-agnostic foundation for offline-first PWAs that must work on cheap Android phones with unreliable internet. Two apps will be built on it: **khata** (credit ledger) and **clinic-queue** (patient tokens). The core provides local storage, sync, online detection, i18n with RTL, and a UI shell. It contains zero app-specific features.

## Scope

**In scope:**
- Generic typed local storage backed by Dexie (append-only records)
- Sync engine with outbox queue, pluggable adapter, retry/backoff, status reporting
- Online/offline detection React hook
- Extended i18n with persistent language selection and per-app translation registration
- UI shell components (AppShell, SyncStatusBadge, LanguageToggle)
- Property-based and unit tests for all of the above

**Out of scope:**
- App-specific record types, reducers, translations, and screens (apps define these)
- A real cloud sync adapter (Supabase) — an in-memory mock is included; real adapter added later
- Server-side / backend implementation
- Authentication
- Conflict resolution beyond id-based merge (append-only model makes this unnecessary)

## Functional Requirements

### 1. Local Storage (Dexie)

**FR-1.1** The system SHALL provide a generic, typed storage API that allows each app to define its own record types (collections) without importing Dexie directly.

**FR-1.2** Every record stored by the system SHALL contain the following base fields:
- `id` — UUID v4 string, generated by the storage API
- `createdAt` — ISO 8601 timestamp, generated by the storage API at insertion time
- `deviceId` — the identifier of the device that created the record
- `collection` — the name of the collection this record belongs to, set by the storage API from the collection key passed to `add`
- `payload` — an app-defined, strongly-typed payload

**FR-1.3** The storage API SHALL be append-only: it SHALL support adding records and reading/querying records, and SHALL NOT support editing or deleting individual records.

**FR-1.4** The storage API SHALL support querying records by collection, ordered by `createdAt` ascending.

**FR-1.5** The system SHALL provide a generic `deriveState` helper that accepts a list of records and an app-supplied reducer function, returning the derived current state. The reducer signature SHALL be `(state: S | undefined, record: Record<P>) => S`.

**FR-1.6** The system SHALL generate and persist a unique `deviceId` per device, stored locally (localStorage). On first use, if no deviceId exists, the system SHALL generate a UUID v4 and persist it. Subsequent uses SHALL reuse the stored value.

**FR-1.7** The system SHALL allow an app to initialize the storage with a named database and one or more named collections, each with a typed payload interface.

### 2. Sync Engine

**FR-2.1** The system SHALL maintain an outbox queue such that every new record added to local storage is also marked as "pending sync".

**FR-2.2** The system SHALL provide a `SyncAdapter` interface with methods to push records to the backend and pull records from the backend. The interface SHALL be pluggable so the backend can be swapped without changing core logic.

**FR-2.3** The system SHALL include an in-memory mock `SyncAdapter` implementation for development and tests that simulates a shared cloud store.

**FR-2.4** When a sync cycle runs, the system SHALL:
1. Pull records from the adapter, passing all locally known record ids so the adapter can exclude them.
2. Merge pulled records into local storage by `id`, inserting only records that do not already exist locally. Each pulled record SHALL be routed to the Dexie table matching its `collection` field (no duplicates, no overwrites).
3. Push all pending records to the adapter.
4. Mark successfully pushed records as "synced" in the outbox.

**FR-2.5** After a record is successfully pushed, the system SHALL mark it as "synced" in the outbox.

**FR-2.6** The system SHALL expose sync status with the following states: `synced`, `pending` (with count), `syncing`, `offline`, and `error` (with message).

**FR-2.7** When the device transitions from offline to online, the system SHALL automatically trigger a sync cycle.

**FR-2.8** The system SHALL allow manual triggering of a sync cycle via a `syncNow()` function.

**FR-2.9** If a sync cycle fails, the system SHALL retry with exponential backoff. Retries SHALL not lose or duplicate records. The backoff SHALL have a configurable maximum number of attempts and a cap on delay.

**FR-2.10** While a sync cycle is in progress, the system SHALL report `syncing` status and SHALL NOT start a second concurrent sync cycle.

### 3. Online/Offline Detection

**FR-3.1** The system SHALL provide a `useOnlineStatus` React hook that returns a boolean indicating whether the device is currently online.

**FR-3.2** The hook SHALL subscribe to browser `online` and `offline` events and update its state accordingly, without requiring a page reload.

**FR-3.3** The hook SHALL return the initial value based on `navigator.onLine` at mount time.

### 4. i18n and RTL

**FR-4.1** The system SHALL support two languages: English (`en`) and Urdu (`ur`).

**FR-4.2** The system SHALL persist the selected language to `localStorage` so it survives app restarts. On startup, the system SHALL load the persisted language; if none is persisted, it SHALL default to `en`.

**FR-4.3** When the active language changes, the system SHALL set `document.documentElement.dir` to `rtl` for Urdu and `ltr` for English, and set `document.documentElement.lang` to the active language code.

**FR-4.4** The system SHALL provide shared skeleton translation keys usable by all apps.

**FR-4.5** The system SHALL allow each app to register additional translation keys per language, merged on top of the shared skeleton keys. App keys SHALL NOT overwrite skeleton keys with the same name; skeleton keys take precedence for shared namespaces.

**FR-4.6** The system SHALL provide a `setLanguage(lng)` function to switch languages at runtime.

**FR-4.7** The system SHALL expose the current language and available languages so UI components can render toggles.

### 5. UI Shell

**FR-5.1** The system SHALL provide an `AppShell` component that renders:
- A header containing the app name, a language toggle, and a sync status indicator
- A content area (children) for the app's screens

**FR-5.2** The system SHALL provide a `SyncStatusBadge` component that displays the current sync status: offline, pending count (e.g. "3 pending"), syncing, synced, or error (with message).

**FR-5.3** The system SHALL provide a `LanguageToggle` component that switches between English and Urdu when activated.

**FR-5.4** All UI shell components SHALL use Tailwind CSS logical properties (e.g. `ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`) so they render correctly in both LTR and RTL layouts.

**FR-5.5** All UI shell components SHALL be mobile-first, targeting screens as small as ~360px wide, with large touch targets (minimum 44x44px for interactive elements).

**FR-5.6** The `AppShell` SHALL accept props for the app name, and SHALL accept the sync status and language controls as built-in (not passed as children).

## Non-Functional Requirements

**NFR-1 Performance:** Local storage operations SHALL complete in under 50ms for up to 10,000 records on a low-end device. Storage queries SHALL use indexed fields (collection, createdAt).

**NFR-2 Reliability:** The sync engine SHALL guarantee that under any ordering of sync operations, interruptions, or retries, no record is lost and no record is duplicated across devices.

**NFR-3 Type Safety:** All public APIs SHALL be fully typed in TypeScript. Generic types SHALL flow from app-defined payload interfaces through storage, sync, and state derivation.

**NFR-4 Offline-First:** The core SHALL have zero runtime dependencies on network availability for local storage and state derivation. Sync SHALL be a background concern layered on top.

**NFR-5 Modularity:** The skeleton core SHALL be organized into independently structured modules (storage, sync, hooks, i18n, ui). The barrel `index.ts` re-exports all modules for convenience. Apps that want to avoid pulling unused code at build time MAY import from sub-paths (e.g. `@skeleton/core/storage`); subpath exports are out of scope for this iteration but the module structure SHALL not prevent adding them later.

**NFR-6 Testability:** All modules SHALL be testable in isolation. Dexie-backed storage SHALL be testable via a Dexie mock or in-memory configuration. The sync engine SHALL be testable with the in-memory mock adapter.

**NFR-7 Accessibility:** UI shell components SHALL meet WCAG 2.1 AA: keyboard navigable, ARIA labels on icon-only buttons, sufficient color contrast, and `dir`-aware layout.

## Constraints

**C-1** The core SHALL be a single npm package `@skeleton/core` consumed by both apps as a workspace dependency.

**C-2** Records are append-only. There is no update or delete operation. Apps derive mutable state from the immutable record log via reducers.

**C-3** Sync merge is id-based: two records with the same `id` are the same record. The first-seen copy wins; there are no field-level merges or conflicts.

**C-4** The Supabase adapter is out of scope for this spec. Only the interface and an in-memory mock adapter are implemented now.

## Testing Requirements

**TR-1 Property-based — sync convergence:** For any number of devices, any sequence of local record additions, and any interleaving of sync cycles (including interruptions and retries), all devices SHALL end with the same set of records (by id), and no records SHALL be lost or duplicated. Use fast-check.

**TR-2 Property-based — state derivation:** For any list of records and any pure reducer function, `deriveState` SHALL produce a deterministic result that equals applying the reducer fold over the records in order. Use fast-check.

**TR-3 Unit — i18n switching:** Tests SHALL verify that switching to Urdu sets `dir=rtl` and `lang=ur`, switching to English sets `dir=ltr` and `lang=en`, and that the selection persists across a simulated reload.

**TR-4 Unit — deviceId persistence:** Tests SHALL verify that deviceId is generated once and reused on subsequent initializations.

**TR-5 Unit — append-only enforcement:** Tests SHALL verify that the `Store` interface exposes only `add` and `query` (plus sync-internal methods), and does not expose any `update` or `delete` method. This is enforced by the TypeScript interface at compile time; the test confirms the public type surface.

---

## Public API Summary

A new app built on the skeleton needs to provide:
1. Its record types (payload interfaces per collection)
2. A reducer function (to derive state from records)
3. Its translations (additional keys per language)
4. Its screens (rendered inside AppShell)

The skeleton provides everything else.
